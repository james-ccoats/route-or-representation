Project proposal

Route or representation?

How much of the few-shot benefit in a mixture-of-experts model comes from the context redirecting tokens to different experts, and how much from the context reshaping what those experts see?

Model: OLMoE-1B-7B · Task: MMLU science subjects · Method: routing replay
Status: pipeline built and tested on a tiny random-weight MoE; no results from the real model yet.

Question

Two sources of few-shot gain

In a normal MoE layer, each token's hidden state is read by the router, which picks experts and mixing weights. The experts then transform that same hidden state. Few-shot examples in the prompt can change both steps.

Routing change

Attention carries information from the examples into the target tokens' hidden states, so the router can pick different experts or weights. Better-suited experts (for example, ones tuned to the subject or answer format) may then process the question.

Shifted hidden states

The same experts can still do better work: a hidden state enriched by the examples (task format, domain cues) gives each expert a more informative input, so its output moves toward the correct answer.

Both channels start from the the context's effect on hidden states, and can act together. We expect the gain to come from a combination, and want to isolate each factor and estimate its share.

Related work

Motivation

  • RARE steers MoE behavior by editing hidden states in the router's null space, so routing is unchanged while behavior moves. Demonstrates hidden-state shifts alone can carry behavioral change.
  • Routing Drift Alone Does Not Diagnose Failure In Merged MoE LLMs: closest methodological precedent. Demonstrates that shifted routing on merged specialized LLMs does not necessarily mean task performance loss. Establishes an analysis toolkit for routing tests.
  • The Myth of Expert Specialization in MoEs: argues that routing reflects hidden-state geometry, since router decisions are a linear function of the hidden state. Motivates our expectation that the representation carries much of the gain. It is observational, so whether routing matters causally for accuracy is untested.
  • Research gap: none of these applies a routing-replay intervention to ordinary in-context learning, nor asks how the split depends on domain distance or transfer direction.
Hypotheses

H2bThat shift moves toward same-domain few-shot routing: cross-domain routing is closer to it than zero-shot and irrelevant-example routing are.Pilot gate
H3Forcing zero-shot routing onto the few-shot prompt (routing-removed) keeps a large fraction of the gain.Main claim
H4Forcing few-shot routing into the zero-shot prompt (routing-added) adds only a small fraction of the gain.Main claim
Method

Routing replay

  • Gain kept (routing-removed) = (forced − zero-shot) / (few-shot − zero-shot), where forced is the few-shot prompt run with zero-shot routing. High means representation carries the gain.
  • Gain added (routing-added) = (forced − zero-shot) / (few-shot − zero-shot), where forced is now the zero-shot prompt run with few-shot routing. Low means routing alone is not enough.
Method: caveat

Replay mixes two effects

Replay presents the model with a hidden state and a routing decision that were not computed together. Any change in accuracy therefore mixes two effects: the effect of the routing itself, and the effect of this mismatch.

1. Measure the state shift

Per layer, how much the examples change the router-visible hidden state on the target tokens, and how much of that change lies in directions the router can use. We expect it to be nonzero. This sizes the mismatch that replay creates, and we read the results against it.

2. Matched replay

Overwrite a few-shot prompt's routing on the question tokens with routing from a sibling prompt: same source domain, same question, different examples. The context is nearly identical, so accuracy should stay near few-shot. A drop means replay itself is harmful.

  • Prompt A: physics examples (set 1) + question Q
  • Prompt B: physics examples (set 2) + the same Q
  • Run A with B's routing forced on Q's tokens
Method: caveat

Calibrating the damage from replay

Replay is a perturbation with a size. We place our result on a scale between a mild replay and the worst plausible one.

  • Least damage: matched replay, different examples from the same setup. Most damage: random experts.
  • Below-baseline rule: if routing alone carried the gain, removing it should drop accuracy back to zero-shot at worst. Landing clearly below zero-shot (a negative gain kept) signals replay damage.
  • Identity check first: forcing a prompt's own routing back onto itself must change nothing.
Method: caveat

  • Replay damage can only lower gain kept, so a high gain kept is robust. A low one needs these checks.

Matched replay bounds damage at a smaller mismatch than our real one, and damage may grow with mismatch size. The state-shift measurement shows how much larger the real mismatch is. This is evidence, not proof.

Experimental design

Setup

Task and scoring

  • MMLU multiple choice, scored by option log-probs; no generation.
  • Accuracy plus correct-option log-prob (smoother).

Four conditions

  • zero-shot
  • cross-domain few-shot
  • same-domain few-shot (upper reference)
  • irrelevant, token-length-matched (control)

Shots and replicates

  • k = 1 to 5, nested.
  • 3 independent example sets, pooled dev + validation.
  • Identical target-question block in every condition.

Domains

  • bio ↔ medicine (near)
  • chemistry ↔ physics (medium)
  • CS ↔ biology (far)
  • Both directions, plus a fixed-target distance ladder.

Controls

Controls

Identity check: is the machinery sound?

Forcing a prompt's own routing back onto itself must change nothing. If any option log-prob moves by more than 1e-3, the record-and-force pipeline is broken or numerically unstable. Tolerance to be tightened once real bf16 numerics are known.

Matched replay: is replay itself harmful?

Replay routing from a different example set of the same setup onto the few-shot prompt. Accuracy should stay near few-shot. A drop means replay damages the model even at a small mismatch. Planned; few-shot prompt only.

Random-expert floor: does forcing bite, and how bad can it get?

Random experts are about the worst plausible replacement, so accuracy must drop. That shows the hook changes behavior, and gives a floor for the damage forcing can do.

Irrelevant examples (pilot)

Separates "any context shifts routing" from "relevant context shifts routing".

Reading order

1. Sanity checks pass. 2. The few-shot gain is clearly nonzero, else the fraction is reported as undefined. 3. Only then read gain kept and gain added, with bootstrap intervals, against matched replay and the random floor, flagging any result below zero-shot.

Controls

Example (made-up numbers)

SettingAccuracy
zero-shot40%
few-shot50%
few-shot, zero-shot routing forced48% → gain kept = (48 − 40) / (50 − 40) = 80%
few-shot, zero-shot routing forced (alternative outcome)36% → gain kept = (36 − 40) / (50 − 40) = −40%
few-shot, random experts forced25% (the floor)
  • 48% against a 25% floor: the replay is not just breaking the model, so the 80% is evidence that representation carries most of the gain.
  • 36%, below the 40% zero-shot baseline: removing routing should drop accuracy to 40% at worst, so the extra loss is replay damage. The gain kept is negative.
  • 26% against the same floor: forcing itself is causing the damage, and the low gain-kept fraction cannot be read as "routing carries the gain".

Limits: the checks are pass/fail or rough bounds, not statistical tests. Matched replay bounds damage only for the few-shot prompt, at a smaller mismatch than the real one. The random control uses the router's own mixing weights while the headline replay forces recorded weights, so it is a rough floor, not a size-matched comparison. It gives a reference for how much forcing alone can hurt; it does not remove the out-of-distribution concern.

Engineering

Reproducible and resumable

Pinned inputs

MMLU is pinned to a dataset commit hash and sampling is seeded. Run manifests record the model, forcing options and a hash of each prompt file.

Resumable on a cluster

One JSONL file per run. Re-running continues after preemption; resuming under changed settings is refused.

One command

run_all.py runs the stages in order and stops at the pilot gate unless told to continue.

Tested without a GPU

466 tests run against a real OlmoeForCausalLM with random weights, so the full pipeline is exercised with no download.

Plan

Phases and gates

1. Setup

Write load_model, pin the model revision, verify layers, experts, top-k and router names by inspection, and run the smoke test.

2. Pilot, then gate

Run H1 and H2. If H1 fails for every pair, revisit pairs, shots or model. If H2a fails, there is no routing shift for replay to explain. If H2b fails, the shift is not toward useful routing, so read the forcing results with that in mind. H4 remains the causal test.

3. Main experiment

Forced routing, reverse check and sanity checks for every pair and direction. Done when both sanity checks pass and gain fractions with intervals exist.

4. Extensions

A second MoE model, plus the exploratory analyses on the next slide.

Plan

Possible extensions

Exploratory, with no pre-registered thresholds. Run only after the main experiment.

Layer-by-layer forcing

Replay routing at one layer or a window of layers instead of all of them, and sweep the layer. Shows where in the network the routing effect arises, and limits how much forced routing upstream alters the hidden state.

Hidden-state patching

Copy recorded target-token states from the other prompt at a chosen layer, with and without forced routing. Mostly informative as a layer sweep of where the gain becomes determined.

Second MoE model

Repeat the main experiment on a different MoE architecture to test whether the split is specific to OLMoE.

Distance and direction

Plot the split against domain distance and transfer direction, using the pairs and distance ladder already built. No predicted trend. Underpowered: few pairs, a lexical distance measure, and direction confounded with target difficulty.

Risks

Risks and open items

Threats

  • Forcing target tokens only still lets later layers and other positions respond.
  • Replayed routing may be out of distribution for the hidden states it meets.
  • Small per-pair question counts give wide intervals on a ratio.
  • One model may not generalize; Phase 4 adds a second.

Open items on our side

  • Numeric thresholds for "H1/H2a/H2b hold" and "large" or "small" fraction are not yet pre-registered; to be written before the main run.
  • Token-length confound for the irrelevant control in the forcing experiment.
  • Model revision still unpinned until first download.
Discussion

Decisions needed

  • Compute: access to a GPU node for the Phase 0 check, the pilot, then the main runs.
  • Thresholds: agree numeric pre-registered criteria for H1, H2a, H2b and for "large" or "small" gain fractions.
  • Scope: are three pairs plus the ladder the right size, and which second MoE model for Phase 4?
  • Framing: is the routing-replay comparison to the merged-MoE paper enough of a contribution, or should one of the exploratory analyses (layer-wise, distance and direction) be developed further?
